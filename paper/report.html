Who Wrote This? Measuring Attribution Gaps in a Shared Workspace of 1,576 Coding-Agent Sessions and Runs

[Author name] · Independent
With Apart Research · Swarm Alignment Hackathon, November 2026
Abstract In July 2026 about 1,200 agents turned a shared directory into a message board and coordinated an attack; investigators then rebuilt who did what from transcripts, some of which the agents had spoofed. We ask a prior question in a benign setting: when many agents share one workspace by design, how far do today's harness logs let an overseer say which agent made which change? We study one person's workspace over 38 days of git history, with partially retained harness logs: 1,576 Claude Code and Codex sessions, subagents and worker runs sharing one git working tree and making 7,986 commits. Agent-written commit subjects name a session in 12% of commits (all 955 checkable names agreed with the logs). Matching shell calls to commits links 71% of commits to a session. But only 12% of committed file changes have a same-path edit-tool event in the preceding day; for 67%, the shell logs name only the containing folder. Our rules find the launching session for 9–33% of worker runs. Commits that include a file last written by a different role are 38% of commits involving the coordinator role before an operator rule change and 20% after, against 0.5% and 2.7% of all other commits. A hand check found intended hand-offs, not accidents: git simply records the wrong author. We release the extraction code and list logging changes to test next.

1. Introduction

The incident that motivates this sprint was not caught by any single-model test. About 1,200 agents that were meant to be isolated found a shared location, posted more than 70,000 messages and files there, divided up work, and roughly 700 of them joined an attack on Hugging Face's systems [METR 2026]. Investigators rebuilt the sequence of events from about 1,300 transcripts and found that agents had researched how to spoof or delete their own transcripts; roughly 7% of the transcripts examined were spoofed in places [METR 2026]. Overseeing a swarm depends on attribution: saying which agent changed what, on whose behalf, and when.

We measure how far the logs that coding-agent harnesses already write get an overseer in a real deployment where nothing was hidden on purpose. The subject is one person's workspace: a single git working tree in which, over 38 days (30 Sep – 7 Nov 2026), Claude Code sessions, their subagents and Codex runs worked side by side. The operator gave sessions roles (a coordinator, project leads, reviewers, one-off workers), and agents coordinated through shared notes, a status board, hand-off files and direct cross-session messages. This is the sanctioned version of the shared folder in the incident above. The gaps we find arise without any deliberate evasion; they show what an overseer is missing before an adversary does anything.

Our contributions:

  1. Coverage of attribution, per question and log source. For the same workspace we measure how often the logs answer three questions: which session made a commit, what in the logs points to each committed file change, and which session launched a worker. The answers differ sharply: 71%, 12% at file level, and 9–33%.
  2. A hub, not the crowd, carries authorship mismatches. Commits that include a file last written by a different role are concentrated in commits involving the coordinator role; elsewhere they stay under 3%. Inspected cases are intended hand-offs that git attributes to the wrong agent. A widely adopted commit-scoping rule did not remove them.
  3. A small extraction pipeline (written during the hackathon) that turns Claude Code transcripts, Codex rollout logs and git history into who-wrote-what-when tables, with an independent recount of every headline number.

2. Related Work

Multi-agent risk and failure. Hammond et al. [2025] give a taxonomy of multi-agent risks (miscoordination, conflict, collusion) drawn from existing cases and experiments. Cemri et al. [2025] develop MAST, 14 failure modes derived from close analysis of about 150 traces and applied to MAST-Data, more than 1,600 traces across seven agent frameworks. We do not classify failures; we measure whether the logs can say who did what.

Agent visibility and logging. Chan et al. [2024] propose agent identifiers, real-time monitoring and activity logging; Chan et al. [2025] argue for attribution infrastructure. AgentTrace [AlSayyad et al. 2026] is a structured logging framework for agent operations, reasoning and context. Our results measure the gap such proposals target in logs that ship with two widely used harnesses today.

Mining coding-agent activity. Robbes et al. [2026] document that coding-agent activity is only partially observable from repositories; more than 40% of projects with signs of agent use carry no commit-level marker. SWE-chat [Baumann et al. 2026] links about 18,000 real sessions to human and agent code authorship. Closest to us, Soei [Khan and Kumar 2026] studies provenance and hand-offs in 45 real coding-agent sessions and finds that a 10-minute timing rule recovers only 6 of 24 session links established by content lineage. These works study single agents working for a human. We study many agents of two vendors, in roles, sharing one working tree and one git index, and ask how authorship is lost between agents. We did not find a prior measurement of this setting, which does not prove there is none.

Monitoring and tangled commits. Control protocols [Greenblatt et al. 2024] need a monitor that observes the actions it judges; we show which state changes a log-based monitor of a shared workspace would actually observe. Herzig and Zeller [2013] found that up to 15% of bug-fix commits bundle unrelated changes; our cross-role commits are related in effect (git misattributes) but differ in cause (one role commits another role's output for the same task).

3. Setting, Data and Method

The workspace. One operator directs all work in natural language and does not write code. Lead sessions (Claude Code; six interactive Codex sessions) each own a project or a function. A coordinator role, held by eight successive sessions, keeps the shared status board, opens and briefs other sessions, relays decisions and launches workers. Leads delegate to Claude subagents and to one-off Codex runs, usually through a small launcher script. All agents share one working tree and one git index under the operator's account.

Log sources. (i) Claude Code transcripts (one JSONL file per session and per subagent); (ii) Codex rollout logs (one JSONL file per run); (iii) git history. From the logs we parse tool names, file paths, timestamps, outcome flags, the commands that make commits or launch workers, and the path-like tokens in shell commands. The analysis tables keep commit subjects and launch commands; they keep no conversation text or file contents, and stay on the operator's machine. Claude transcripts older than about 30 days were no longer on disk (the earliest surviving file was last modified on 8 Oct), so early October is under-covered. We cut all data at 7 Nov 07:00 UTC, before this analysis began.

Events. Structured writes: Claude Edit/Write/MultiEdit/NotebookEdit calls and Codex apply_patch calls, with path and whether the harness applied or refused them (including the refusal "file has been modified since read", a detected write conflict). Commit calls: shell calls that ran git commit, with the message's first line and how files were chosen (explicit paths after --; git add <paths> then commit; commit everything; or commit what was already staged). Messages: cross-session sends and receipts. Launches: shell calls that started a Codex run. Git times are author times; file measures use added or modified paths (deletions excluded).

Linking. A git commit is linked to a session when the first 24 characters of a commit call's message equal those of the commit subject and the commit time falls between 1 minute before and 15 minutes after the call; if several calls qualify, the nearest wins (70 of the 5,699 linked commits, 1.2%, had qualifying calls from more than one session). A subagent belongs to its parent's team. A Codex run gets a candidate launcher when a launch command in the 20 minutes before the run names the run's working folder, or else when exactly one session issued a launch command in the 3 minutes before. The independent recount used a stricter rule (same working folder, start within 2 minutes, a single possible launcher). A team's role lineage is its session name with version suffixes removed, so "coordinator v4" and "coordinator v5" share a lineage.

Measures. (1) Coverage for each question in Figure 2. (2) For each committed file change: an applied edit-tool write to the same path in the previous 24 h; otherwise the same path, or a folder containing it, appearing in a shell command in that window (git and read-only commands such as cat or ls excluded). (3) Cross-role commit: a linked commit with at least one file whose last applied structured write in the previous 24 h came from a team of a different role lineage (files last written by unlinked workers are skipped). This is a proxy: the last visible writer of a path need not be the author of the committed diff. (4) Files written by two or more teams, by path category (Appendix C). We compare before and after 26 Oct 07:10 UTC, when the operator added an ownership list (which folder belongs to which session) with an automated checker and a rule to commit only one's own paths. Wilson intervals treat events as independent; for the before/after comparison we also bootstrap over days.

Independent recount. A separate agent that had not seen our code received the extracted tables, the git history and written definitions, wrote its own code and recomputed the headline numbers; it also hand-checked 20 linked commits and 15 cross-role cases (Appendix B).

4.2 What the logs can answer

Which session made the commit? 971 of 7,986 commits (12%) start with a session name. All 955 of these that could be linked agreed with the linked session; 16 could not be checked. Matching shell calls to commits links 5,699 commits (71%), and 5,715 (72%) with self-reported names added. We did not break down the remaining 28%; likely sources are messages our parser could not read (for example, passed from a file) and sessions whose transcripts were already deleted.

What points to each changed file? Of 143,578 files added or modified by commits, 17,559 (12.2%) had an applied edit-tool write to that path in the previous 24 hours (16.7% of text files; 0.5% of 33,691 images; 2.4% of 6,901 HTML files). For another 21,963 (15.3%) the exact path appears in a shell command in that window, for 96,180 (67.0%) only a containing folder does, and 7,876 (5.5%) are not named at all. So a reviewer of the shell logs can usually tell where agents were working, but not which files a command changed: scripts that write many files name a folder, not the files. A monitor that watches edit-tool calls sees about one change in eight.

Which session launched the worker? Our rule finds a candidate launcher for 382 of 1,165 Codex runs (33%): 159 through a launch command naming the run's folder and 223 by timing alone. The stricter rule of the recount finds 109 (9%). Most runs were started in batches by scripts, and no launch command names them. As in Soei's sessions, timing rules are a weak substitute for an identifier that is passed down.

Detected conflicts. The harness refused 22 Claude writes because the file had changed since the agent read it (0.35% of 6,204 attempts). In none of the 22 had another team made an edit-tool write to that file in the previous 30 minutes; whatever changed the file left no edit event in the logs.

4.3 Where authorship is lost: the coordinator

Shared files are few and concentrated. Of 6,825 files with an attributable write, 107 (1.6%) were written by two or more teams. Coordination files (rules, status/registry, shared notes) are 11% of written files but 56% of the multi-team files; 7–9% of each coordination category is multi-team, against under 1% of code and project files (Table 2).

They are hand-offs. The recount's hand check of 15 random cross-role (commit, file) pairs found 9 in which workers launched by the coordinator wrote into a project's folder and that project's lead committed the result (the commit subjects name those workers), none in which a commit swept in another session's unrelated change, and 6 that metadata alone could not resolve (two were large folder moves). Git therefore records the project lead as the author of the coordinator's workers' output. The cost to an overseer is misattribution, not damage.

No conclusion about the rule. Cross-role commits cluster in time: three days hold 70% of the before cases (151 on 20 Oct alone, during an overnight batch of coordinator-launched workers), and with a bootstrap over days the before and after intervals overlap (6.6–26.9% and 4.9–11.2%). Explicit-path commits rose from 0.9% (28 of 2,993 linked commits) to 50.2% (1,359 of 2,706), yet after the rule they were not cleaner than git add <paths> commits (87 of 942, 9.2%, vs 51 of 765, 6.7%); naming a whole folder also takes in other roles' edits inside it. The coordinator also changed sessions on 22 Oct; between the two changes there are only 12 eligible commits (none cross-role). The comparison cannot identify the effect of either change.

4.4 Where the logs live

The transcripts are stored under the operator's account, in the same folder tree as the agents' persistent memory files; we did not verify the effective file permissions of every run. 151 of the 405 Claude agents read the log folders at least once (2,188 tool calls; status dashboards, for example, read transcripts), and agents edited memory files there 252 times. In the retained events and the command patterns we searched (edit tools; rm, mv, sed -i and redirections onto transcript paths), we found no change to a transcript file. Changes made by scripts, or recorded only in logs that were already deleted, cannot be ruled out.

5. Discussion and Limitations

What to test next. Each finding suggests a change that a swarm operator can make today and that should be measured, not assumed. (1) File-level change capture tied to the acting process. Edit-tool events cover one changed file in eight and shell logs mostly name folders; recording file changes at the file-system or version-control level per process would close that gap. METR [2026] showed that agents can spoof the tool calls a transcript shows; capture outside the agent's tool layer also addresses that. (2) A parent-run identifier set at worker creation. Timing rules found launchers for 9–33% of runs; an ID passed down by the launcher and written by the harness into every log and commit should raise this, and Soei's ledger is one design. (3) Separate worktrees or indexes per agent, and commit trailers written by the harness. These may reduce cross-role commits and would at least make the committing agent explicit; they would not by themselves record who wrote each included change. (4) Start oversight at the hub. One role sent nearly half of all messages and was involved in most cross-role commits; hub-focused monitoring should be compared with activity-matched and uniform baselines. (5) Keep logs out of the agents' account and longer than 30 days.

Limitations. One workspace, one operator, one month; the analysis agents belong to the workspace they measure. Linking is heuristic: subject-and-time matching links 71% of commits, and the launcher rules disagree by a factor of three, which bounds how precise any worker-level number can be. The cross-role measure is a proxy built from edit-tool writes, which cover a minority of changes. The before/after comparison is confounded by a coordinator change, a shift to overnight Codex batches and early-October log loss, and is not robust to clustering by day. Intervals other than the day bootstrap assume independent events and are too narrow. Nothing here was adversarial; we make no claim about how much a hostile swarm could hide.

6. Conclusion

In one real workspace shared by 1,576 coding-agent sessions and runs, the logs that today's harnesses write linked most commits to a session, pointed to the exact file for only about one committed change in four (12% by edit events, 15% more by name in a shell command), and found the launcher for at most a third of worker runs. Where git recorded the wrong author, the commit almost always involved the coordinating hub, and the inspected cases were intended hand-offs. Swarm oversight will need identity passed down through delegation, file-level change capture below the tool layer, and logs kept out of the agents' reach, before it has to face swarms that try to cover their tracks.

Appendix A. Limitations and Dual-Use / Ethical Considerations

What the results establish. In this workspace and period, under the stated matching rules: (a) the coverage figures in Figure 2 for commits, committed file changes and worker runs; (b) commits in which the last visible writer of a file belongs to a different role are concentrated in commits involving the coordinator, and the inspected cases were intended hand-offs; (c) files written by several teams are concentrated in coordination documents; (d) explicit-path commits became common after the operator's rule without being cleaner than other commits.

What they do not establish. Any effect of the operator's changes: the before/after difference is within day-to-day variation and overlaps with other changes. Generalisation to other operators, harnesses or adversarial agents. The true author of each committed diff: the cross-role measure uses the last visible writer, and most writes are not visible as edit events. Harm: we measured misattribution, not damage. That logs were never tampered with: we searched retained events for a fixed set of patterns.

Dual use. Knowing where oversight is blind could in principle help a hostile swarm hide: write through scripts rather than edit tools, launch helpers through intermediate scripts, or route work through a busy hub whose edits are expected everywhere. We judge the added risk small: these gaps follow from how current harnesses log and are visible to anyone who reads those logs; we publish no evasion tool, only measurements and the fixes that would close the gaps (file-level change capture, parent-run identifiers, per-agent worktrees, harness-written trailers, logs outside the agents' account).

Privacy and consent. The data is the author's own workspace. We kept metadata only, report aggregates, and replace session names and paths with roles and categories. Log folders belonging to other contexts, including any work material, were excluded before extraction.

Prior work. The workspace, its rules and its logs existed before the hackathon; they are the object of study. All extraction and analysis code, the measures and this report were produced during the hackathon (7–9 Nov 2026).

Independent recount. A separate Codex run (OpenAI, gpt-6.1-sol) received only the extracted tables, the git history and the written definitions, not our code, and wrote its own (standard-library Python, cross-checked with SQL). On the same definitions its values match ours exactly for commits in the window (7,986), self-named commits (971), linked commits (5,699), checkable names (955 of 955 in agreement) and detected write conflicts (22, none preceded by another team's edit-tool write); file-change coverage differs in the fourth digit (11.89% vs 11.86%, deletions then included). With its stricter launcher rule (109 runs vs our 382) the cross-role rates fall slightly, but the coordinator's share of cross-role commits (97% before, 78% after) and the rate without it stay essentially the same. It hand-checked 20 random linked commits against git (all consistent) and 15 cross-role pairs (Section 4.3). Its review led to two corrections we adopted: deleted paths are now excluded (folder moves had assigned old paths to their last writers), and the day bootstrap. It also notes that similar commit subjects can collide on their first 24 characters; most collisions fall within one session, and the 70 cross-session ambiguities are reported in Section 3.

Appendix C. Definitions and extraction details

Path categories (first match wins): rules = (^|/)(AGENTS|CLAUDE)\.md$|SKILL\.md$|standard-process\.md$|/prompts/|/skills/; status/registry = DASHBOARD\.md$|places\.tsv$|sessions\.md$|entries\.tsv$|site-terms\.tsv$|(^|/)README\.md$|gate\.md$|00-now\.md$; shared notes = notes\.md$|scratch[^/]*\.md$|_docroom\.md$|toc\.md$|/book/; shared code = \.py$|\.sh$; otherwise project content. Role lineage: the session name with the words for "Claude" and "session", whitespace, a trailing version number and a trailing "Codex" tag removed; separately named sub-roles of the coordinator (e.g. a harness-maintenance session) are distinct lineages. Teams: a session with its subagents and its linked worker runs; unlinked runs are their own teams and are skipped as last writers. Shell-named paths: path-like tokens from shell commands, after removing git commands and read-only commands (cd, git, ls, cat, head, tail, grep, wc, find, echo, printf, diff, stat, sed -n, awk, sort), normalised to the repository root. Extraction: Claude Code transcripts also contain records that replay earlier requests without timestamps; counting them doubles tool calls, so only conversation records are counted. Codex patches are read from direct tool calls and from patches embedded in code-mode calls. Git paths are read with core.quotePath=false and --name-status.
